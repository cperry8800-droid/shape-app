## 2 · What the coach experiences (the whole 0% loop)

**Bringing a client at 0% commission** — two paths, both attribute to the coach:

1. **Invite a member on Shape** (add-client sheet → search → Invite): sends a
   real 1:1 DM (`coach_invite` card) AND writes a client-bound `coach_referrals`
   row (`create_coach_referral`). The DM card carries no token — the referral row
   IS what resolves 0% at checkout. If the referral write fails, the row shows a
   **Retry 0% tag** action (re-runs only the referral, never a duplicate DM).
2. **Share the ref-tagged link** (✉ Email / ✆ Text / ↗ Share): the durable
   `?ref=<token>` link (`create_coach_referral_link`, one per provider, reused).
   A member who opens it while signed in **binds** it (`bind_coach_referral` —
   the touch that starts/refreshes the 30-day window). Buy inside the window → 0%.

**Seeing the result** — the coach Business page: a "Bring your clients · 0%
commission" plate (copy/email the link + raw URL for an Instagram bio) and a
"who found whom" zone labelling every client **You brought · 0% fee** vs **Found
you on Shape · 15% fee**, keyed off the STORED `fee_bps` (subscriptions AND
recent one-time purchases).

## 3 · Architecture you'll need (anyone touching the fee/attribution rails)

- **The stored `fee_bps` is the billing truth, full stop.** Roster labels,
  analytics MRR, refunds, payout notifications all read the per-row stored rate —
  NEVER re-derive from `origin` + the current constant. A future BYO/marketplace
  rate change alters no existing row. `ISSUED_FEE_BPS` (src/lib/coach-origin.mjs)
  is the append-only registry of every rate an origin has been stamped at; a rate
  change APPENDS (keeps the old), so in-flight sessions persist what they charged.
- **`attributionPair(origin, feeBps)` is the write-once guard.** Origin and fee
  are validated as ONE unit before hitting a money row — only marketplace/1500,
  coach_invite/0, coach_link/0 survive; every other combination downgrades WHOLE
  to marketplace/1500. Both webhook write paths resolve the pair ONCE and reuse it
  for the upsert, the schema-cache-lag gate, and the payout notification.
- **The origin resolver lives in the DB** (`resolve_coach_checkout_origin`,
  SECURITY DEFINER, auth.uid()-scoped) and owns the whole precedence: **waitlist
  wins** (an ACTIVE invite only — `status='waiting'` OR `invited AND
  invite_expires_at > now()`) → provider-matched token touch → unexpired
  client-bound row → marketplace. A user route NEVER reads the referral ledger via
  the service role — resolution runs on the CALLER's RLS client. Fail-closed
  marketplace/1500 on any error (incl. pre-migration, when the RPC is absent).
- **Schema-cache lag is the subtle one.** Right after the migration, PostgREST can
  briefly not know `origin`/`fee_bps` (PGRST204). The webhook's
  retry-without-columns is GATED to default-pair writes only — a BYO delivery in
  that window fails 503 so Stripe redelivers (nothing side-effectful runs before
  the write), because defaulting would freeze a 0% BYO row as marketplace/1500
  under the write-once trigger FOREVER.
- **`buildOriginFeed`** (src/lib/origin-attribution.ts) is the shared feed both
  analytics routes call — folds subscriptions + recent paid one-time purchases,
  each labelled from its stored pair. Honest-data: unknown name → `—`, unknown
  price → `null` (never `0`); a genuine read fault logs + degrades to subs-only.
- **`resolvedRole` is the add-client sheet's single readiness authority** (mobile).
  All invite/share state keys by `role:userId`; `resolvedRole` is reset on every
  role change and stamped only when the current role's provider lookup settles, so
  no post-switch stale frame can ship the previous role's token/provider. If you
  touch that sheet, keep that discipline — 6 of PR B's review rounds were closing
  render-frame gaps in exactly this state machine.

## 4 · The web `?ref=` capture (public/supabase.js)

`window.ShapeCoachRef` captures `?ref=<uuid>` on ANY page load, binds it once a
signed-in session exists, and re-binds on re-open (fresh touch). Checkout
passthrough: `livingShared.jsx` POSTs `body.ref`; the legacy `/subscribe` +
`/purchase` server-action forms carry a hidden ref field (`CoachRefField` —
URL param first, stored fallback, and it persists a direct-URL ref BEFORE the
signed-out `/login` redirect can drop it). Client storage is hygiene only — the
server re-validates token + provider + window on every resolve.
