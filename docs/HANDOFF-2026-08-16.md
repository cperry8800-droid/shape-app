## 2. What pull request #1891 ships

The 2026-08-15 wave made sign-out scrub the **signing-out tab**. It wrote down two things it
did not close. This closes both.

### 2.1 Cross-tab sign-out

Before this, `sessionStorage` was per tab by specification, and sign-out only cleared the tab
it ran in and then reloaded that one document. There was **no** `storage` event handler, no
`onAuthStateChange` handler and no `SIGNED_OUT` handler anywhere in the source — so a second
open tab kept `shapeLiveWorkout`, `shapeLiveWorkoutResult` and all of its in-memory user
state until somebody closed it. On a shared device that is precisely the inheritance the wave
set out to stop.

Now the scrub stamps **`shape.signedOutAt`** with a nonce (a `storage` event fires only on a
**changed** value, so a constant stamp would be silent on the second sign-out), and all four
surfaces listen:

| surface | file |
| --- | --- |
| website pages on the shared shell | `public/newdesign/pageShell.jsx` |
| website legacy fallback client | `public/supabase.js` |
| mobile application at `/m/` | `mobile-app/src/broadsheet/iosAppBroadsheetMain.jsx` |
| Next.js dashboard | `src/components/SignOutButton.tsx` |

`pageShell.jsx` and `supabase.js` share one install guard (`__shapeSignOutListener`) because
both can load on the same document.

### 2.2 Owner-scoped career award queue

`shape.careerAwardPending` stored a bare post identifier with **no owner**. Session
initialisation replayed it for whoever was signed in; `award_work_milestone` matches
`author_id = v_uid`, so for a different account it returned `{granted:false,
'not_a_milestone'}` **with no error**, and the client then removed the key on any non-error
response. In the exact shared-device scenario this wave is about — person A signs out, person
B signs in — B's session submitted A's post identifier under B's identity and then silently
destroyed A's retry.

Now there is **one localStorage key per claim**:
`shape.careerAwardPending.<userId>.<postId>`, value `Date.now()`. Replay only happens on a
matching user identifier, so an unrelated account can neither submit nor destroy another
person's pending award.

Nine of the fifteen were priority one. **Nearly every one was the same shape: a rule applied
to one surface and not to its siblings.** A finding points at a line, so it reads as a bug
report about a location; it is almost always a report about a **rule**, and rules have call
sites, sibling implementations and twin copies that have not been enumerated.

⚠ **The findings-per-round curve was flat** — 2, 3, 3, 2, 2, 2 — which is this repository's
own documented signal to **stop patching and change approach**, not to patch again. What
finally ended it was moving the rule to the **chokepoint**: the token drop and the broadcast
both now live in the scrub, which every sign-out path already calls. Placing them per-surface
cost three rounds on its own, because a `storage` event never fires in the tab that wrote it —
so receivers had the behaviour and initiators did not.

**The lesson to carry, written down in full:** before pushing a fix for a review finding, ask
*which surfaces does this rule not reach?* and grep for the sibling handlers, the other
initiators and the twin copies. If the rule has three or more call sites, move it to the
chokepoint rather than fixing sites one at a time. And note the sub-case that bit twice here:
the sibling is sometimes **your own previous fix**.

## 4. Round seven in full — refuted on the version, not patched

**The finding** (`src/components/SignOutButton.tsx:89`, "Verify cookie deletion before
broadcasting"): the two sign-out routes discard `signOut()`'s result and return HTTP 200
unconditionally, so gating the broadcast on `res.ok` supposedly lets a tab broadcast while
the session cookie is still valid — a sibling dashboard would then reload straight back into
the departed member's session with no corrective event.

**The mechanism is correct.** `src/app/api/auth/signout/route.ts:12` and
`src/app/api/auth/session/route.ts:58` both `await supabase.auth.signOut()` with no error
check and return 200 either way.

**The consequence does not hold on this code path.** Both routes build their client through
`createClient()` → `@supabase/ssr` **0.12.4** → `@supabase/supabase-js` and
`@supabase/auth-js` **2.111.0**, and in 2.111.0 `_signOut` removes the local session
**before** returning the failed-revocation error:

```js
// node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:3420-3431
const { error } = await this.admin.signOut(accessToken, scope);
if (error) {
  if (!(isAuthApiError(error) && (404 | 401 | 403) || isAuthSessionMissingError(error))) {
    if (scope !== 'others') { await removeCurrentSession(); }   // ← removal happens here
    return this._returnResult({ error });
  }
}
```

That removal writes through the `setAll` adapter in `src/lib/supabase/server.ts:20-31`, and
`applyShapeCookieOptions` deliberately passes `maxAge: 0` deletions through untouched
(`src/lib/supabase/cookie-options.ts:36` — the carve-out exists precisely so the 30-day
session policy cannot resurrect a cookie the SDK is trying to delete). In a Route Handler
`cookies()` is mutable, so the deletion lands in the response. On an authentication-service
outage the 200 therefore still carries the `Set-Cookie` deletion: `res.ok` and "the cookie is
gone" agree.

The one branch that returns an error **without** removing is `GoTrueClient.js:3415` — a
`sessionError` out of `_useSession` that is not "session missing", meaning the session could
not be read at all. There is no valid session in that state for a sibling tab to reload back
into.

**All four initiators hit those same two routes**, so the conclusion covers every surface the
finding names: `pageShell.jsx:349` and `index.html:1197` (POST `/api/auth/signout`),
`SignOutButton.tsx:82` and mobile `shapeBackend.js:563` (DELETE `/api/auth/session`).

**The proposed remedy was declined, and the reason matters more than the decision.** Making
the routes return a failure when `signOut()` reports an error would suppress the broadcast in
exactly the outage where the cookie **was** deleted — leaving every sibling tab signed in
after a sign-out that actually completed. Under this pull request's own rule (*a missed
broadcast leaves siblings as they were; a premature one manufactures a signed-in tab nothing
corrects*) that fails in the wrong direction, and it buys nothing the library version does not
already provide.

⚠ **Record the divergence, because it is the mirror of a rule this repository already
carries.** The website's **vendored auth-js 2.108.2** (`public/vendor/supabase-js-2.108.2.umd.js`,
integrity-locked) *does* return the failed global revocation **before** `_removeSession()` —
which is exactly why its `scope:'local'` retry is load-bearing there. That governs the
**localStorage** session and is handled by the scrub's own retry plus
`shapeDropPersistedAuth()`. The **cookie** path in these routes runs 2.111.0. Two versions
apart, same function, opposite ordering. **Re-read `_signOut` before bumping either bundle** —
a bump silently flips the assumption on whichever side moves.

## 5. Invariants — do not "simplify" these

- ⚠ **The token drop and the broadcast live in the scrub**, the chokepoint every sign-out path
  already calls. Placing them per-surface cost three review rounds.
- ⚠ **This origin hosts two Supabase clients.** `public/supabase.js` pins
  `storageKey: 'shape.auth'`; the mobile client sets **none**, so auth-js falls back to its
  default `sb-<projectRef>-auth-token`. `shapeDropPersistedAuth()` clears **both**. A
  configuration the code does not set is still a configuration the library sets — "no
  `storageKey`" is a *different default*, not an absence.
- ⚠ **Listeners scrub with `broadcast:false`.** A receiving tab that re-stamps
  `shape.signedOutAt` echoes into a loop across every open tab.
- ⚠ **Every initiator gates its broadcast on a confirmed cookie deletion** (`res.ok`), for the
  reason stated above: a missed broadcast is recoverable, a premature one is not.
- ⚠ **The per-claim award keys are prefix-shaped**, and the scrub sweeps by prefix. A test
  asserts that no `SHAPE_SCRUB_PREFIXES` entry matches them — without it, the owner's ruling
  to keep the durability queue silently reverses and every queued award is wiped on sign-out.
- ⚠ **`/m/` ships under the website's origin** (`scripts/build-m.sh`), so both surfaces share
  one `localStorage`. The canonical scrub inventory is the union in
  `public/newdesign/localScrub.mjs`; mobile imports it, and the two website classic-script
  copies (which cannot import an ES module) carry inline copies gated by
  `tests/local-scrub-sync.test.mjs`. **Any future key change must touch all three copies or
  the suite goes red — that is the design.**
