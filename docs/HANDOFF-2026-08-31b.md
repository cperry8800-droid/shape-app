## 3. Architecture a next session needs

### The subject freeze — and why `security definer` would silently disable it

`2026-08-31-review-note-subject-freeze.sql` makes `session_id` · `client_id` ·
`snapshot_date` · `reviewer_id` immutable on UPDATE. Two properties are load-bearing:

1. **The trigger function is SECURITY INVOKER, and must stay that way.** The first cut
   added `security definer` and made the whole trigger a **no-op**: under DEFINER,
   PostgreSQL sets `current_user` to the function OWNER, so the `is_privileged` early
   return fires for **every** caller. Measured rather than argued — one temp function
   each way after `set local role authenticated`: definer sees `postgres`, invoker sees
   `authenticated`. The file carries a 12-line DO-NOT-RE-ADD note, and the structural
   `DO` guard **fails the apply on `prosecdef`** so the no-op cannot return silently.
2. **`is distinct from`, never `<>`.** Each subject column is NULL on the other's rows,
   and `NULL <> NULL` is NULL, which PL/pgSQL's `IF` reads as **false** — a plain `<>`
   would let a subject swap through the guard entirely.

It is a **freeze rather than a re-stated policy** deliberately: re-checking subject
access in the UPDATE policy would put one security rule at a **third** site to keep in
sync (INSERT policy, `can_access_review_note`, UPDATE policy), which is exactly the drift
this migration set already warns about. Editing a note's WORDS stays legitimate;
repointing one at a different person never is.

### The store: one authority, and it is the database

`public.store_catalogue` is the charging authority *and* the validation set for free
tier picks. Anything that removes or reprices an item is therefore **at least** a
migration + `src/lib/store-catalogue.ts` + the mobile list + the website list, held
together by `tests/store-catalogue-sync.test.mjs` — and, since #1988, **the older
migrations that would resurrect it on replay**, held by
`tests/store-migration-replay.test.mjs`.

### Where the profile hero's numbers come from

`BSSignalCoachProfile`'s cover height (460) and gradient stop (76%) are derived from
`BSSignalSigil`'s `size` prop plus the fixed chrome above it. If the sigil is resized,
re-derive both — the photo silently stops reaching the hexagon otherwise, which is the
exact complaint #1990 fixed.
