### #1876 → `ed3582a1f` — the RPC restore + the meal-note honesty fix

`public.get_or_create_direct_conversation` was declared by
`2026-05-02-conversations-messages.sql` and **never created in production** — one of
eight declared-but-absent functions, and the only one live product code calls.

**Three things worth carrying forward, none of them the diff:**

1. **`null not in (…)` is not true.** It evaluates to NULL, and PL/pgSQL's `IF` treats
   NULL as false, so the original's bare membership guard was bypassed by the one value
   it existed to reject. It was *silent* rather than loud because of a three-part
   coincidence: the column is **nullable**, a **CHECK passes when it evaluates to
   NULL**, and the partial unique index's predicate **excludes NULL rows**.
2. **The sibling sweep was closed by measurement.** Target-column nullability is the
   deciding test — nullable means silent junk, NOT NULL means a loud 23502. Four of the
   five comparable guards are NOT NULL, so nothing else was owed.
3. **The review's proposed remedy for the meal-note claim was wrong** and was
   deliberately not implemented. Recorded so nobody "restores" it: it keys on a `null`
   that cannot distinguish *failed* from *never attempted*; awaiting the sibling promise
   can suppress the notice entirely (no timeout); and copy nudging a re-log
   double-counts `add_meal_macros`, an accumulating upsert with no idempotency key.

**Migration verified live, behaviourally — not just by source shape.** The migration's
own guard is a `prosrc` **text** match, which proves shape and not behaviour. So: the
function gates on `auth.uid()` first, and impersonating a signed-in member with
`set_config('request.jwt.claims', …, true)` gets past that. A null-role call then
returns `Invalid provider role.` with the `conversations` count unchanged at 0. The
whole probe was wrapped in a `raise exception` so it rolls back regardless of outcome.
**Reuse this for any `SECURITY DEFINER` function whose guard needs live testing without
leaving rows behind.**

## ⚠ The RPC's caller inventory — read this before touching it

Three callers, three failure modes. **Do not narrow the `authenticated` grant.**

1. `api/nutrition/meal-note/route.ts:135` — **was silent; is now VISIBLE, because #1876
   fixed exactly this.** The route still answers HTTP 200, but on a delivery failure it
   returns `ok:false` with `failedCount` and `reason:'delivery_failed'`, and the client
   surfaces "We couldn't reach your coach"
   (`iosAppBroadsheetClient.jsx:2424-2458`). ⚠ Note `delivered:false` **alone** is not a
   failure signal — it is also the valid `no_coach` state, which stays deliberately
   quiet. Describing this path as silent is pre-#1876 history; do not carry it into
   incident analysis.
2. `api/messages/direct/route.ts:84` — **loud** (400).
3. `mobile-app/src/services/shapeBackend.js:1990` — `supabase.rpc(…)` **directly from
   the client**, through no API route, via `sendProviderMessage` (`:2022`). Reached
   from the marketplace panel (`iosAppBroadsheetMarketplace.jsx:2119`) and **only for a
   real listing** — `resolveCoachProvider` (`:1886`) requires `provider_id`/`db_id`, so
   demo coaches and the meal/exercise-swap flows (which pass `{name, provider_role}`
   with no id) resolve to null and save locally **without calling the RPC**.
   **Semi-loud** when it does call.

**All three execute as `authenticated`.** Both API routes use the anon key with the
caller's own session — `createClient()` (`lib/supabase/server.ts:13`) and
`clientForRequest` (`lib/request-auth.ts:14-24`). **Nothing calls this RPC as
`service_role`**, so narrowing the grant breaks all three — and the mobile one
**semi-loudly**, which is the dangerous kind: it catches, saves the thread to
localStorage, and shows "Message saved locally" *with the error text*
(`iosAppBroadsheetMarketplace.jsx:2129-2136`). The member sees a success-shaped notice
and the coach never receives the message, so nothing reads as an outage.

**No in-app path can send a null role**, so the RPC's null guard is a backstop:
`normalizeProviderRoleForMessages` → `normalizeRole` returns `'client'` and can never
produce null. A genuine NULL needs a hand-made PostgREST call.

## Traps this session paid for

- **`null not in (…)` evaluates to NULL, and `IF` treats NULL as false.** Textbook
  three-valued logic, and it still shipped. A **CHECK also passes when it evaluates to
  NULL**, and a partial unique index with an `is not null` predicate silently exempts
  the row. The three compose into a guard that rejects nothing.
- ⚠ **A reviewer's throwaway supporting detail is a claim too.** I verified the
  headline of a P2, then copied its parenthetical ("the swap flows call it too") into
  **two files** without a single grep. It was false. I had already learned to verify a
  finding's mechanism, consequence and remedy — the aside slipped through all three.
- ⚠ **When correcting a factual error, write LESS, not more.** One finding produced
  three, and every one was prose I *added while fixing*. A correction is the
  highest-risk place to elaborate, because the reader trusts it twice over. 1 → 3 is a
  **rising** curve: change the approach, don't patch again.
- **A verification method can fail in the direction that looks like success.** Three
  times today: the `git push` Dependabot banner reported 2 high vulns when the API shows
  **0 open**; a **source-text** migration guard proves shape, not behaviour; and the
  CRLF check below. Cross-check with a second instrument before believing a scary *or* a
  reassuring number.
- ⚠ **`grep -c $'\r'` is not a usable CRLF check *in the Claude Code Bash tool on this
  Windows box*.** On a pure-LF file it returned **13857** — the file's exact line count,
  identical to `grep -c ''`. **Scope matters and the first draft of this line overreached:**
  a reviewer ran the same command in its own Linux shell, where `$'\r'` expands normally
  and correctly returns 0, so this is *not* a general property of Bash and no mechanism
  should be asserted for it. What is safe to carry forward is the practice: verify line
  endings with a **binary read** (`b.count(b'\r')`) or `tr -cd '\r' | wc -c`, never the
  `grep` form, and never trust a saturated count that equals the line total.
- **A clean Codex pass arrives as an issue comment; findings arrive as a review
  record.** Both name the reviewed commit — check it matches the head, because a clean
  verdict on a stale commit looks identical in the API.
- ⚠ **Summarising a precise fact drops the part that carries the risk.** This handoff's
  first draft compressed "four variables across two secret stores" into "three variables
  in Codemagic" — losing `VITE_SENTRY_DSN`, the *only* one that enables capture, and
  pointing Android at the wrong store entirely. The WORKLOG had it right; I paraphrased
  it wrong. **When a handoff item is a list of credentials or steps, copy it exactly or
  cite the source — do not compress it.** Corollary learned the same way: *"the DSN is
  live"* is true of the **web** and says nothing about the APK or IPA, which are built
  by different pipelines from different stores.
- **Prove a comment-only edit rather than asserting it.** Both migration edits were
  verified by hashing the executable SQL with comments stripped
  (`38131a6601feaa46`, unchanged) and confirming no non-comment line appears in the diff.
