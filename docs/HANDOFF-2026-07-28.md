## What the guardrail is

Advisory load flags on a coach-authored training week. It says when the week just
written is an unusually large jump **for that client**, and it never blocks, never
rewrites a week, and never proposes an alternative. Red costs a coach one extra
click.

Load is **session RPE × duration** in arbitrary units. Three regimes:
**`cold_start`** (no usable baseline — the launch regime, since `workout_sessions`
was empty at design time), **`measured`** (the ramp curve read at the client's own
baseline), **`return`** (after an interruption, where the cap reduces the baseline
and the ordinary ramp is then read at the reduced number — **the cap is not the
ceiling**).

Two live axes, volume and concentration, plus a registered but **disabled**
`distribution` axis that votes on nothing.

## The doctrine — the parts that are decisions, not implementation

- **A skipped rating is NULL, never 0, and is EXCLUDED from load maths** rather
  than imputed. A 0 would compute `0 × minutes = 0 AU` and enter a real week at
  zero, deflating the baseline and tightening every future ceiling.
- **The derived estimator was specified and CUT.** Averaging `workout_set_logs.rpe`
  measures a different construct with a systematic downward bias — and a perverse
  one, since the same working sets score lower when a client logs more warm-up
  sets. Worse, it would have converted unrated sessions into pseudo-rated ones, so
  a week that ought to degrade to cold start would qualify as *measured* on a
  contaminated baseline. **If the skip rate turns out high, the fix is prompt UX,
  not a silent estimator that hides the signal.**
- **`unknown` is not a pass.** It carries no axes, no red path and no baseline, and
  it always says why — rendering nothing would be indistinguishable from green.
- **An unconfirmed overrun is excluded**, and credibility is **derived at read
  time, never stored** (§13.8). The row carries only the FACTS — was the member
  prompted, and what did they answer. A stored verdict would have silently
  reclassified old rows the moment the ceiling was retuned, which §13.4 promises.
- **Beyond ten hours a session is EXCLUDED, not malformed.** Our own wall-clock
  fallback produces it, so calling it a caller bug would turn one forgotten timer
  into a whole-history `unknown` — and `unknown` never blocks publish, so the
  guardrail would switch itself off in the dangerous direction.
- **Exclusion biases the weekly total downward**, which tightens future ceilings.
  That is a known and deliberately accepted property: the error runs in the
  conservative direction, and the alternative is inventing load that was never
  rated.

## The defect review caught, and why it mattered most

The rating first shipped **inline, below the button that ends the workout**.
`Finish workout ✓` saved and navigated away, so a member following the primary
call-to-action never saw the prompt.

Nearly every session would have stored a NULL rating — and a week counts as
`measured` only when **more than half** its sessions are rated. So **no client
would ever have left `cold_start`**, the ramp curve would never have executed, and
the whole reason capture shipped ahead of its consumer (accumulating rated
sessions from day one) would have quietly failed. The spec had already called for
a completion prompt on one screen; the placement, not the content, was wrong.

It is now a dedicated completion step, and the binding rule on it is:
**backing out still saves the workout, with a null rating.** The rating is
optional; the log is not. There is deliberately **no "Skip rating" affordance** —
skipping stays possible, it is never invited.

The duration facts ride in the existing `summary` jsonb, **not a new column**:
jsonb accepts an unknown key on any deployment, so it needs no migration and
cannot reproduce the `session_rpe` schema-cache window, where an unapplied column
rejects the whole insert and costs a member their entire session log over one
optional field.

## Two failure classes worth carrying forward

1. **A `[]`-dep effect cleanup captures the FIRST render's closure.** The unmount
   safety net would have saved a junk zero-duration session with no sets, because
   the `finishSession` it closed over held `sessionRpe: null`, an empty `setLogs`
   and ~0 elapsed. Fixed with a ref re-pointed every render. Nothing in the
   pipeline catches this — it is valid syntax, typechecks, builds and passes.
2. **A positional function called with an options object returns early, and the
   test then compares two nulls.** `bsLocalWeek(startedAtISO, timeZone)` was called
   as `bsLocalWeek({startedAtISO, timezone})`, so it bailed on line 1, the zone
   cache was never touched, and `deepEqual(null, null)` passed. The guard against a
   repeat is to assert the fixture produced a real value before comparing anything
   to it.

3. **Don't assert a test's own premise.** A guard test pinned
   `Date.parse('2026-02-30…')` as finite, reasoning it would "fail loudly if V8
   changes its mind". But it fails in exactly the case where **nothing is wrong** —
   an engine returning NaN there is *more* correct, and `bsLocalWeek` still rejects
   the date, because the calendar check runs before the parse. Loud failure is only
   worth having when it means something broke. **Assert the behaviour you own, not
   the runtime's bug.**

All three were caught by **review, not by the suite**. The perturbation sweeps are
the counter-measure: 50 mutations attempted on the core — **46 killed, 3 documented
equivalents, 1 unusable** (its target string no longer exists; the fact it aimed at
is guarded by a sibling mutation that was killed) — plus 14 on the completion step
and 4 on the late guards, including faithful reproductions of every defect either
reviewer found.

## ⚠ MALFORMED vs EXCLUDED — read this before touching 2b

The single most important contract in the module, and the one that shipped wrong
mid-PR.

**`malformed` is reserved for shapes NO LEGITIMATE WRITER CAN EMIT.** Everything
else is **excluded** from load, and the rest of the week still scores.

It matters because **one malformed row turns the WHOLE evaluation `unknown`, and
§7.5 rules that `unknown` never blocks publish.** So mis-filing a row as malformed
does not fail safe — it switches the guardrail **OFF**, which is the dangerous
direction, arriving through the guard meant to stop it.

What that looked like in practice: an over-max (>600 min) duration was reported
malformed. But our **own wall-clock fallback produces exactly that row** when a
phone is left on the completion screen — so a forgotten timer would have disabled
the guardrail for that client. It is now **excluded**. The rule in one line:
**a value our own code produces is never a caller bug.**

The converse applies too, and two cases were added under it:

| Shape | Verdict | Why |
|---|---|---|
| duration > 600 min | **excluded** | our wall-clock fallback emits it |
| `not_prompted` / absent answer | **excluded** | never asked ≠ affirmed (F22) |
| **fractional** duration | **malformed** | `integer` column; both writers round |
| **calendar-impossible** date | **malformed** | `timestamptz` cannot hold Feb 30 |
| negative / non-finite duration | **malformed** | unproducible |

⚠ **`Date.parse` does not reject `2026-02-30` — it silently MOVES it.** V8 falls
back to its legacy parser and normalises the day to **March 2**, so the session
bucketed into a real ISO week it was never part of and fed the wrong baseline,
with nothing anywhere to say so. Month 13 and hour 25 *do* return NaN; **day
overflow is the only case that slips through**, which is why a finite-check looks
sufficient and isn't. Rejected explicitly by calendar arithmetic.
