## Load-bearing designs (don't re-litigate)

- **`coach_reviews.owner_id`** is server-derived by a SECURITY DEFINER trigger
  from the slug (non-forgeable, CWE-639), stamped on insert, **immutable for an
  identity-stable edit**, **re-derived on a slug/kind repoint**, and it **honors
  the FK `on delete set null`** (a NULL clear passes through so account deletion
  works). **NO backfill** — every heuristic mis-attaches after a slug
  rename/reuse, so all pre-migration rows stay NULL forever (write-path stamping
  only).
- **Film keys are PER-ROLE:** coach P1 → `profile_custom.film` (coach-media),
  member M5 → `filmMember` (member-films). The normalizer takes `opts.filmKey`.
- **`member-films`** is a DEDICATED video-only bucket, NOT a `community-photos`
  widening (photo paths don't check `file.type`).
- **Account-delete purge** (`/api/account/delete`) is robust end to end: every
  user bucket (incl. the film buckets) with re-list-from-start (no >1000 skip),
  sub-folder recursion, interleaved-page pagination, storage-purge-FIRST with
  abort-on-failure, and a post-delete sweep of the writable window. Deliberately
  service-role (documented admin-erasure exception).

### Declined in review — written rationale, accepted residual

- **RLS-scope the account-delete storage purge** — `/api/account/delete` is
  service-role **by design**: several purged tables (`user_goals`, which holds
  the health profile, plus `user_integrations`/OAuth tokens, `score_ledger`,
  `messages`, and the coach rows) have **no user-facing DELETE policy**, so an
  RLS-scoped client would *silently* fail to erase exactly the most sensitive
  data while reporting success. Every delete is scoped to the verified caller's
  own id. No work planned unless the ruling changes.
