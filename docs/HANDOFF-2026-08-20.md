## 2. What shipped

**The prep sheet asks WHY before it starts, and the answer changes the schedule.** The
owner ruled the three options are three *different questions*:

| Option | Means | Runs |
|---|---|---|
| Cook at the same time | weave the work, shortest session | `TOGETHER` |
| Cook separately | finish one, start the next | `SEQUENCE` |
| Cook to serve | everything completes at one moment | `SERVE` |

"Cook at the same time" had been running **SERVE with no serve time** — so two of the three
doors led to the same room, and the option meant to get the cook *out of the kitchen* was
optimising for landing dishes together. Measured over 3,570 catalog pairs, TOGETHER
finishes sooner in **16.0%** and later in **4.2%**; it is the faster plan on balance, but
the reason it is correct is that it is a different question.

**The engine.** One placement now answers for the timeline, the serve time *and* the
issues. A pull names the resource that caused it. A serve search that runs out of
iterations falls back to the serial bound rather than returning an empty timeline, and
clears `exact` when it does.

## 3. The honest limits — read these before promising anything

- ⚠ **"Cook to serve" does not usually deliver a single moment.** It lands every dish
  together in **2.2%** of pairs (mean gap **15.6 min**). It is **not the kitchen** — an
  unlimited-station kitchen measures *identically*. It is the **one cook**, who cannot
  finish two hands-on dishes at the same instant. The sheet discloses the gap beside the
  start time. **Closing this is a scheduler design change**: model the cook as the scarce
  resource and optimise against that. Do not describe it as a tuning job.
- ⚠ **71 of 85 recipes still schedule short** against their own annotations (1,817 min
  total). The scheduler honours what the annotations say; the annotations understate what
  the recipes do. **This is a DATA pass over step text, not an engine one.**
- ⚠ **The pull reason code has no UI consumer.** `BS_SERVE_ISSUE.STATIONS` vs `.COOK` is
  correct now, but nothing on screen tells a cook which one held their plan apart.
- ⚠ **Tuna macros are still an OWNER RULING**, carried from the USDA wave.
- ⚠ **The serial fallback is unreachable on real data** — it needs a recipe past
  `BS_ORCH.serveSearchMax` steps where the catalog's largest is **8**, and the search is
  already ~17s at 320 steps. It makes the failure honest; it does not make that session
  usable. Do not cite it as a capability.

## 5. Two findings refuted — do not "fix" these again

- **"The serial fallback can itself fail."** Mechanism real, consequence not: the named
  case (100 one-minute steps against 1) returns a complete 101-event timeline, and 11
  shapes converge including 7- and 8-dish sets past the exhaustive permutation bound. The
  uneven pair is pinned as a regression case.
- **"The Pidgin subtitle is a sentence fragment."** So are all 13 locales, the English
  source included (*"On the table at a time you choose"*) — it sits under the option
  title. ⚠ The *adjacent* Pidgin finding **was** taken: `by {t}` for a clock time
  contradicts the locale's **own** convention (`for {time}`, three instances across coach
  and marketplace).

## 6. Traps that cost real time this session

- **The mount harness installs no translator**, so copy renders with placeholders intact
  (`Within {n} min of each other`). That is deliberate —
  `tests/kitchen-allergen-surfaces.test.mjs` asserts on the literal template. To assert on
  a real number, install an interpolating `window.ShapeI18n` **scoped to one test**, as
  `tests/cook-serve-schedule.test.mjs` does. Do not change the shared harness.
- **CI builds the PR merge commit**, not the branch head. A branch green on its own can go
  red the moment something merges to `main`. When it does, re-pin catalog-dependent tests —
  and check the re-pinned test still *discriminates*; one of ours was one edit away from
  becoming decoration.
- **`\n` inside a shell heredoc collapses.** Build multi-line anchors with `chr(10)`, or
  write the script to a file first. This cost two broken edits today.
- **Inserting into `warroom.ts`**: anchor on the object's opening `{`, not on its
  `section:` property — a sibling object dropped inside an object literal is a parse error.
- **A War Room `status` flip is not enough.** If the label still says "NOT BUILT", the
  entry now contradicts itself. Rewrite the label, and say what shipped *differently* from
  what the item asked for (ours specified a disabled-with-reason state; the sheet discloses
  the gap instead).
