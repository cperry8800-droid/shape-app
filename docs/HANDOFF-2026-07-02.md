## What shipped (`#1495`)

- **Feature.** When a coach is **at capacity** (`isEffectivelyAtCapacity`), signed-in members
  join a **waiting room** to be first in line. The coach invites a client back with a **7-day
  first-dibs** window — a live invite is the ONLY thing that lets an at-capacity coach be
  purchased/subscribed (checked in `checkout-session` + `purchase` + `subscribe` via
  `hasActiveWaitlistInvite`). A completed Stripe payment/subscription flips the row to
  `booked` (webhook). Clients can **withdraw** (waiting→left / invited→declined). **Coach
  discretion** on who to invite (positions are shown, but not a locked FIFO — the owner's call;
  CodeRabbit accepted this and withdrew its FIFO flags).
- **Surfaces.** Mobile client CTA + coach room panel (`iosAppBroadsheetClient.jsx`, via the
  `window.ShapeWaitlist` bridge in `shapeBackend.js`) + both website profiles
  (`public/trainer-profile.html`, `public/nutritionist-profile.html`).
- **New API routes.** `POST /api/waitlist/join`, `GET /api/waitlist/mine`,
  `POST /api/waitlist/withdraw`, `GET /api/waitlist/room`, `POST /api/waitlist/invite`.

## Architecture you'll need (the RLS-authoritative waitlist pattern)

This is the reference for any future waitlist-adjacent work — the repo policy
(`.coderabbit.yaml`, `src/app/api/**`) treats a **service-role write for a USER action as a
BLOCKING security regression**; admin is only for system writes (notify / webhook / cron).

- **Caller-scoped client for user actions.** `resolveRequestClient(request)` in
  `src/lib/waitlist.ts` returns `{ user, supabase }` — an RLS-scoped client from a cookie
  session OR a Supabase Bearer token (so web + mobile both work). `join` / `withdraw` and the
  first-dibs check (`hasActiveWaitlistInvite`) run on THIS client, gated by the table's own-row
  RLS policies. `hasActiveWaitlistInvite` now **throws** on a lookup error so callers surface a
  retryable state instead of silently denying first-dibs.
- **`coach_waitlist` RLS** (migration `supabase-migrations/2026-07-01-coach-waitlist.sql`):
  - SELECT own; INSERT own-as-`waiting` **only into a room that EXISTS and is at capacity**
    (the INSERT `WITH CHECK` mirrors `isEffectivelyAtCapacity`); UPDATE own only FROM
    `waiting|invited` (USING) and only TO `left`/`declined`/`waiting` (WITH CHECK, where
    `waiting` is allowed only for a fresh row or an **expired** invite — a live invite can't be
    reverted).
  - **`coach_waitlist_guard_cols` BEFORE INSERT/UPDATE trigger** freezes `created_at` +
    `provider_role`/`provider_id`/`client_id` (and the invite timestamps unless transitioning
    to `invited`). This is what actually stops queue-jumping / moving a spot to another coach /
    spoofing invite timing — RLS `WITH CHECK` can't see the OLD row, so the trigger pins them.
- **Cross-user reads/writes → `SECURITY DEFINER` RPCs** (verify `auth.uid()` ownership
  internally; same idiom as `get_roster_weekend_split` / `get_client_stats`):
  - `get_my_waitlists()` — the caller's active entries + FIFO position (clients can't read peers
    under RLS, so position is computed here). "Active" = `waiting` OR `invited AND
    invite_expires_at > now()`.
  - `get_coach_waitroom(p_role, p_provider_id)` — roster + client names (joins `profiles`) +
    position; raises `42501` for a non-owner (route maps → 403).
  - `invite_from_waitlist(p_entry_id)` — ownership-checked, atomic flip of
    waiting/declined/expired-invited → invited; raises `42501`/`P0002`/`P0001`; guards against a
    second active row (→ clean 409, not a 23505). The route maps a racing `23505` → 409 too.
- **Response shapes the consumers expect** (don't rename without updating mobile + both
  websites): `join → {entryId, position, status}`; `mine → {entries:[{id, providerRole,
  providerId, status, note, invited_at, invite_expires_at, position}]}`; `room →
  {entries:[{id, clientId, clientName, note, status, position, created_at, invited_at,
  invite_expires_at}]}`; `invite → {ok, invite_expires_at}`. The RPCs return `queue_position`
  (`position` is a **reserved word** in a Postgres `returns table`); the routes alias it back to
  `position`.
- **Pure logic twin.** `src/lib/waitlist.mjs` (`computePositions`, `isActiveWaitlistRow`,
  `ACTIVE_WAITLIST_STATUSES`, `WAITLIST_INVITE_TTL_DAYS=7`) mirrors the SQL FIFO/active
  predicate exactly — an `invited` row with no/`<= now` expiry is NOT active. Tested in
  `tests/waitlist.test.mjs`.

## Review journey (lessons)

- **Four rounds.** (1) `8bd99c26` the RLS rework + the original 24 CodeRabbit + 2 Codex
  findings; (2) `f7c7d99c` a **Postgres reserved-word** fix — `position` can't be an unquoted
  column in `returns table` (→ `queue_position`) + `#variable_conflict use_column` on the
  plpgsql fns; (3) `d648252a` the incremental re-review (INSERT-room-exists, live-invite-revert,
  strict UUID, error-surfacing, marketplace-filter, FIFO tiebreak `(created_at, id)`); (4)
  `31186c8b` the **at-capacity gate** in the INSERT policy.
- **Adversarial review workflow** (4 dimensions — security/RLS · CodeRabbit-resolution ·
  correctness/races · migration-SQL — each finding independently refuted) + the automated
  security-review pass caught **two real MAJORs before commit**: the UPDATE-`USING`
  queue-jump/un-book and a join↔invite reactivation race. Note: 5 verify agents got
  rate-limited mid-workflow — recover dropped findings from the finder agents' `agent-*.jsonl`
  and adjudicate by hand (that's how the queue-jump + others were caught).
- **No local Postgres.** The migration can only be validated by the owner running it (surfaced
  the reserved-word error). Review the SQL carefully + keep it idempotent; `#variable_conflict
  use_column` is a cheap safety net for OUT-param/column ambiguity at call time.
- **CodeRabbit "done" detection** (still true): read the *current* summary-comment body +
  resolved-thread state via **GraphQL `reviewThreads{isResolved}`** — the REST `position` field
  and the literal "Actionable comments posted:" string are unreliable. CodeRabbit **accepts
  documented by-design replies** (it withdrew the FIFO flags after the coach-discretion reply).
