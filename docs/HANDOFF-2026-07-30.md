## What shipped since the 07-29 handoff

### `dd913c410` — the website publish gets a date, and the hole closes

The owner's ruling, verbatim: *"Give the flow a date. 'Publish & Send to Client'
gets a date picker and goes through the evaluated boundary like every other coach
write. No carve-out — the wave's premise is one evaluated door."*

`publishClientWorkout` (`public/supabase.js`) was a **live, unevaluated insert
that created UNDATED workouts**, and the evaluated boundary refuses an undated
session by name (an undated row has no week, so there is no load to judge). It now
requires a `scheduledDate` and posts to `/api/trainer/workout`.

That unblocked **item 2 of the 07-29 "Next, in order"**, so the RLS lockout shipped
too (`2026-07-31-coach-insert-lockout.sql`, migration 3 above). The doctrine is now
**structural rather than conventional**: a future surface cannot reintroduce the
hole by writing the table directly, because the database refuses it.

⚠ **It closes the unevaluated CREATE, not every unevaluated mutation.** The trainer
UPDATE policy still lets a coach move an existing session's date without
re-evaluation. Narrowing it breaks Nora's undo (`src/lib/ai/actions.mjs` archives a
row through it) and needs its own ruling — **registered, not silently folded in.**

Also in that commit, and worth knowing: the date picker's `min` attribute is an
**affordance, not a gate** (the handler reads `.value`, so a typed or pasted past
date still arrives), and the payload strips base64 file **bodies** — base64 inflates
~33%, so a 2 MB PDF would blow the API's 1 MB JSON cap and make the workout
undeliverable. That path used to bypass our API entirely, so the cap is new exposure.

### `e5475481b` — the review round

Seven fixes. Full reasoning is in the commit body; these are the ones that outlive it.

**A 4xx was reported to the coach as a successful publish (CRITICAL).**
`postWeek` gated its throw on `status >= 500`, so a 400/401/403/409 fell through
with no `results` → `results=[]` → `rejected=[]` → **`status:'accepted'`**. An
expired session, an RLS denial, and the boundary's own validation refusal all told
the coach the week landed. **Judge a refusal path by its FAIL DIRECTION, not by
whether it returns.**

**A gate handed zero evaluations does not hold — it opens.**
`bsAdjustProposedWeeks` returned `[]` when `todayISO` was absent, and `[]` is
indistinguishable from "this plan affects no week". It now refuses. The existing
test *pinned* the old behaviour with reasoning that was half-right (don't default
to a clock read — correct) and wrongly concluded (so return nothing).

**Sort on what is HASHED.** `weekRequestHash` tie-broke on the synthesized `s${i}`
id — the submission index wearing a name — while the digest stores `id: null`. Two
sessions on the **same day** with no caller id (a two-a-day, or a separately
authored finisher) hashed differently by submission order, so the ledger read one
logical week as two legitimate publishes and wrote it **twice**. Every pre-existing
order test used sessions on *different* dates, so the tie-break never ran.

**`pg_temp` must be listed (CWE-426).** Unlisted it is searched **first**, ahead of
even `pg_catalog`, so unqualified catalog calls in a definer body are shadowable and
run as the owner. Swept the class rather than the flagged line: `track_event` had it
too.

**The cap must only trim the far tail.** An unordered `.limit(400)` gets an
arbitrary 400 rows (Postgres guarantees no order without ORDER BY), so a long
history could truncate the *current* weeks away and regenerate against a partial
plan. 390 rows is three saved 26-week programs. Windowed to the planner's own scope
(strict future + undated repeats) and ordered nearest-first.

**The drain no longer absorbs the server's answer.** Both triggers are
fire-and-forget, so a held week the guardrail **refused on replay** was dropped in
total silence — the same failure the drain was built to fix, one level up. It now
emits `shape:assignDrain` and logs. ⚠ **Owner scoping was deliberately NOT re-added
client-side**: `assignQueue.mjs` removed that heuristic on purpose (it drifted
across three review rounds) and `publish_client_week` re-verifies the coach
server-side. What was missing was the refusal *surfacing*.

**The 409 reason reaches the coach.** `dashBuilder` parsed the guardrail's sentence
into an `Error` and the catch threw it away for a fixed "try again" — advice that
can never work, since retrying an unchanged week returns the same 409 forever. It
renders the reason now, and names how many weeks actually landed before the stop
(they stay live; silence read as "nothing was written").

## Traps this session paid for

- **A reviewer's `outdated` flag is not evidence.** It means the anchored lines
  changed, not that the defect is gone — and re-wiring parked code can make a stale
  finding live again. Split unresolved findings by `isOutdated`, then verify.
- **A test can pin a bug and explain itself while doing it.** The fail-open above
  shipped with a comment arguing for it. Read what a test *asserts*, not what its
  comment claims.
- **Editing an applied migration means a RE-RUN, so it must be re-runnable.** A bare
  `create function` raises 42723 the second time and takes the whole transaction —
  including the grant block — with it.
- **Don't test telemetry by writing telemetry.** A post-condition that *calls*
  `track_event` inserts a real analytics row with a null user. Inspect
  `pg_get_functiondef` instead — the house pattern.
- **`.limit()` without `.order()` is a silent sampler**, not a cap.
- **The design hook flags this repo's own house grammar.** The 3px accent left-spine
  is the documented Open Ledger / Wire Dispatch motif (14 uses across
  `public/newdesign/*.jsx`); `side-tab` findings on it are false positives. Classify,
  don't churn — and don't suppress without the owner's word.
