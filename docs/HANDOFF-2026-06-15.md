## 3. The Session-details page — architecture you'll need

### Mobile (`mobile-app/src/broadsheet/iosAppBroadsheetClient.jsx`)
- **`BSActivityDetail({ d, ... })`** — the full-screen page (portals into
  `#bs-phone-surface`). `d.focus` is `'stats'` (Session details — workout numbers
  only) or `'comments'` (the conversation + composer). Opened from the feed card
  via `openDetail(focus)` → `setActivityDetail({...})` in `BSClientFeed`.
- **`AreaChart({ vals, color, invert, fmt, idKey, height })`** — the reusable
  Strava-style chart defined *inside* `BSActivityDetail`: 3-tick y-axis,
  x-axis **mile markers** (only when distance is in miles), faint gridlines,
  filled area. `invert: true` puts the LOW value on top (pace — faster reads
  higher).
- **Categorization** (top of `BSActivityDetail`): `allStats` = `d.detailStats`
  minus the hero stat. The **top Summary holds every scalar that doesn't have its
  own chart**; only cadence/elevation (when charted → shown as the chart's chip)
  and best-pace/top-speed (the velocity chart's chip) are excluded. `outputStats`
  is now always `[]` (the bottom Output grid is intentionally dead — left in place,
  never renders).
- **`paceCfg`** — the per-sport switch (Pace vs Speed, invert, formatter, chip).
- Data flows in via **`bsActivityFromPost(p)`** → reads
  `p.rawMetrics.{hrTrace,cadenceTrace,elevTrace,paceTrace,powerTrace}` + `zones`
  (from `bsBuildZones` reading `zoneDurations`) + `breakdown` (splits/sets).
  `openDetail` forwards all of these + `sport: _rawType`.

### Website (`public/newdesign/dashboardCommunity.jsx`)
- **`SessionDetailsModal({ p, onClose })`** + **`WebAreaChart`** — a faithful port
  of the mobile page (same rule, same sections), opened from a **"Session details →"**
  card on activity posts in the dashboard Community feed.
- Live posts carry their metrics through the feed mapping into a `session` payload
  (`{ metrics, stats, sport, title }`). The feed GET (`/api/community/feed`) already
  returns the full `community_posts` row including `metrics`.
- **Demo run card** (Jonah W.) carries an example `session` so the signed-out
  preview shows it. Helpers: `fmtPaceSec`, `sessArr`, `buildZonesFromDurations`.
- **If you edit this file, bump `dashboardCommunity.jsx?v=` on the 6 shells**
  (ClientApp/ClientCommunity/TrainerApp/TrainerCommunity/NutritionistApp/
  NutritionistCommunity). Current: `?v=20260615b`.

### Live data (`src/app/api/integrations/strava/sync/route.ts`)
- **`fetchStreams(token, activityId, sport)`** — ONE streams call per NEW activity
  pulling `heartrate,cadence,altitude,velocity_smooth,watts,distance`. Velocity is
  converted **per sport** (mph for rides / sec-per-100m for swims / sec-per-mile
  for run·walk·hike). Cadence ×2 for foot sports → spm; altitude → ft.
- **`resampleByDistance(values, distance, N, scale)`** — resamples each metric
  **evenly by distance** (cumulative-distance interpolation) so the chart x-axis is
  true distance; falls back to `downsampleStream` (time-uniform) when there's no
  distance stream (indoor/treadmill).
- Stored as `metrics.{hrTrace,cadenceTrace,elevTrace,paceTrace,powerTrace}`, flowed
  through `communityPostFromRow.rawMetrics` (mobile `shapeBackend.js`).
- Gated: **NEW posts only**, capped at `STREAM_CAP = 24` per sync (rate limit).
- **WHOOP** (`src/app/api/integrations/whoop/sync/route.ts`) has no per-second
  streams → zones + stats only, honestly trace-less.

### THE GRAPH-TYPE RULE (canonical — also in `docs/WORKLOG.md` 2026-06-15)
Primary velocity chart is sport-specific; everything else is data-gated and
renders only when its real series exists:
- **Pace** (M:SS, y-axis inverted) → run · walk · hike
- **Pace /100m** (M:SS, inverted) → swim
- **Speed** (mph, not inverted) → ride/cycle; **Power** (W) is its own chart when a
  power meter is present
- **Heart rate** = bpm area + Z1–Z5 labeled zone bars → ANY activity with HR (incl.
  strength)
- **Cadence** (spm/rpm), **Elevation** (ft terrain) → whenever the stream exists
- **Splits** = column chart (mile splits / ride intervals / working **sets**)
- **Summary** = hero + all chartless scalars; **no bottom Output section**

**Gotchas learned this session**
- The `cp -r mobile-app/dist public/m` **must run from the repo root** in its own
  Bash call (each call starts at `/home/user/shape-app`; a prior `cd mobile-app &&`
  in the *same* command makes `cp` fail with `cannot stat 'mobile-app/dist'`).
- Website `public/newdesign/*.jsx` are **static** (not in the Next build) — parse-check
  catches syntax only; they load React/Babel from a **CDN**, so they **cannot be
  rendered headless offline**. Verify visuals with a faithful **static HTML mock** +
  headless `chromium_headless_shell` (see `/tmp/*.html` examples in this session).
- **Bump `?v=` cache-busts** on every page that references a shared `.jsx` you change.

## 5. The dashboard "phantom gap" fix (so you don't reintroduce it)

`DashDemoBand` (the signed-out "Preview · demo data" notice, defined in
`public/newdesign/dashToday.jsx`) was rendered **before** the `position:fixed`
site header on every dashboard page → it was hidden behind the header yet still
pushed the spacer + all content down (~33px of empty space under the nav). Fix:
it's now a **fixed BOTTOM banner** (out of the top flow), like the mobile preview
banner. Also removed the 6px top padding on the three dashboard `<main>`s. **If you
add any top-of-page element to a dashboard, keep it out of the flow above the fixed
header.**
