## Cooking engine review

The existing engine already offers step-specific ingredients, labeled timers, completed/skipped steps, a screen wake lock where supported, optional step narration and voice commands, and a meal-prep flow. This pass focused on interruption recovery: previously the saved place relied on explicit exit and did not retain active timers/checklists.

`cookResume.mjs` now validates persisted session fields. `BSCookMode` autosaves solo method/plated state on interaction and restores the current step, checked ingredients/prep, completed/skipped steps, elapsed start and timer deadlines. Timers count real time spent away; expired timers remain visible. Recipe fingerprint, local day and account must match. A recovered plated cook remains saved until logging or explicit completion. Storage failures are shown instead of promising recovery.

Browser check: started a four-minute sear timer, advanced to step 5, reloaded without pressing End, reopened the recipe and resumed step 5 with 1:55 left and elapsed time retained. The timer subsequently expired visibly. Existing recipe-fingerprint tests and new timer/state tests pass.

Remaining product improvements, not implemented in this PR:

1. Persist and restore an entire multi-dish prep session. It currently owns a separate flow and intentionally does not use the solo resume slot. Preserve recipe order, each dish's progress and timer ownership together.
2. Add native scheduled timer notifications for locked/backgrounded phones, with permission and cancel/reschedule handling. Current recovery retains deadlines, but foreground timers are not a guarantee of background sound. New exit copy is explicit about this.
3. Consider a time-based recovery window for overnight cooks. Current recovery intentionally expires at the local calendar-day boundary and stores one solo session on this device; it is not cross-device synchronization.

Native voice/background/lock-screen behavior and authenticated meal logging still require device/account verification. No new promises were added for those capabilities.

## Radio screenshot diagnosis

The bars were already full-width at Medium text size. The actual screenshot defect came from app-level CSS zoom: `getBoundingClientRect()` returned scaled dimensions which were then assigned to canvas CSS pixels and scaled again. At Small (0.9), a 366px wrapper contained a 329.4px canvas with a right-hand gap.

`BSRadioSignalField` now uses `clientWidth/clientHeight`, CSS `100%` dimensions and viewport-to-local conversion for the measured figure. The existing full-width band and centered spectrum mapping remain intact. Small and Large layouts both measured 366px canvas/366px wrapper and were visually checked. The regression executes the real sizing/measurement code across 0.9/1/1.12 scales and narrow/wide layout sizes. Device pixel ratio remains capped at 2.
