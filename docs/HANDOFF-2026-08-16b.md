## ⚠ READ THIS FIRST — the wave changed shape at round 12

**The age gate no longer admits on absence.** Rounds 9→12 ran **1 → 1 → 4 → 4** findings,
each round finding defects in the previous round's fix. Every one of round 12's four P1s
reduced to one sentence: *a session exists, `date_of_birth` is null, and the gates treat
null as not-a-minor, so the account is admitted.* Patching write surfaces could not
converge — each patch added a new failure mode — because the hole was the **read-time
default**, not any one writer.

So the approach changed, on an **owner ruling**: `mustRefuseForAge()`
(`src/lib/age-derive.mjs`) now requires proof of **adulthood**. A usable DOB decides both
ways, the trigger-written `over_18` is the fallback, and a row proving nothing is refused
unless it predates **`ADULT_PROOF_REQUIRED_FROM`** (2026-08-16). A **null/absent profile
REFUSES** — precisely the state a failed provisioning write leaves behind.

**Things that will bite you if you do not know them:**

- **`created_at` is the grandfather's proof and is now server-controlled** (stamped on
  INSERT, immutable on UPDATE, service_role exempt). Verified behaviourally on production:
  impersonating a member, a backdating UPDATE came back unchanged.
- **The cutoff is a ONE-WAY RATCHET.** Moving it forward re-admits every unproven account
  created in the widened window. A test fails the build if it moves.
- **Both gates MUST `select('… created_at')`.** Forgetting it makes every account read as
  unplaceable and refuses **everyone**. A test pins both selects.
- **Three migrations `create or replace` `set_over_18()`** (2026-06-22, 08-15, 08-16) and
  all are marked safe to re-run, so **every one carries the full body**. A test scans the
  whole migrations directory; a definition dropping either freeze fails the build.
- **Coaches submit a DOB now** (owner-directed), collected on both application forms,
  re-validated in `/api/apply`, stored in `provider_applications.dob`, and carried into the
  profile on approval without overwriting an existing date. Approval **refuses** an
  application it cannot age-place.
- **`/api/apply` is migration-safe**: it retries without `dob` on `42703`/`PGRST204` and
  carries the validated date in `details`, so those applicants stay approvable.

## Codex round 9 found a P1 — REAL, and now FIXED (was: "needs an owner ruling")

**Codex reviewed `53cdd22bf` and returned one P1** ([discussion_r3791731789](https://github.com/cperry8800-droid/shape-app/pull/1888#discussion_r3791731789)),
on the exact claim the trigger comment asked it to check. **I reproduced it — it is real:**

```
DOB 2008-08-17 | instant 2026-08-17T00:30:00Z
America/Los_Angeles    localday 2026-08-16 | adult locally: false | JS adult: true  | ADMITS A MINOR EARLY
America/New_York       localday 2026-08-16 | adult locally: false | JS adult: true  | ADMITS A MINOR EARLY
UTC / Europe/London / Asia/Tokyo / Pacific/Kiritimati                              | agrees
```

The UTC day runs **ahead** of every zone west of UTC, so there `isMinorFromDob` declares
adulthood **before the member's local eighteenth birthday** — up to ~11h early
(Pacific/Niue, UTC−11). The header's claim that the asymmetry "only ever refuses for one
extra day rather than admitting a minor early" was **false west of UTC**, i.e. the comment
ruled out the exact thing the code was doing.

**First pass (`88ca063ba`):** the false safety claim was removed and replaced with the
verified counterexample. A one-directional guarantee in a comment is worse than the bug,
because it tells the next reader not to look.

**Second pass — the behaviour itself is fixed: adulthood is asserted only once it is true
in EVERY timezone.** The calendar day is read at **UTC−12** (`ADULT_REFERENCE_OFFSET_MS`,
the "anywhere on Earth" convention) — one subtraction before the existing clamped
comparison. No tz database lookup, no extra query, no migration.

- **The cost runs in the safe direction and is bounded:** a member is refused for up to 12h
  after local midnight at UTC (26h at UTC+14) on the day they turn 18. Refusing an adult
  briefly is a nuisance; admitting a minor is the failure this gate exists to prevent.
- **The `exactly 18 today is an ADULT` contract survives** — "today" now means today
  everywhere. Every vector was re-anchored to **12:00Z** (the instant at which the AoE day
  equals the UTC day); a bare `Date.UTC(y,m,d)` is midnight, which is still the previous day
  at UTC−12, so unshifted vectors would silently test the wrong day.

## What round 8 fixed (`53cdd22bf`)

**P1 — the age gate admitted a real minor for one day, and the two gates disagreed
about them.** `isMinorFromDob` derived its adult cutoff with
`Date.UTC(year - 18, month, day)`, which **rolls** an impossible anniversary forward
(Feb 29 → Mar 1), while Postgres `date - interval '18 years'` **clamps** it back
(Feb 29 → Feb 28). So on **Feb 29 of a leap year**, a member born exactly 18 years
earlier on **Mar 1** — 17 years and 364 days old — read as an **ADULT** in JS and a
**MINOR** to the `set_over_18()` trigger.

That is the unsafe direction, and it is the two derivations disagreeing about one
person, which is the entire reason the shared module exists. Both cutoffs were verified
against **production Postgres**: `2028-02-29 - interval '18 years'` = `2010-02-28`.
Recurs 2028, 2032, 2036…

The fix takes day 0 of the following month (= the last day of the intended one). Only
February can roll, but the guard is written generally.

⚠ **The 11 original vectors covered a leap-day BIRTHDAY and never a leap-day REFERENCE
DATE** — the one boundary the file was written to protect was the direction it did not
test. The new vector is **mutation-tested**: 12 pass with the clamp, **11 pass / 1 fail**
without it.

  `isMember:false` and exits via **402**, not 503. `refuseKnownMinor` by contrast reads
  `error` explicitly and **fails OPEN** by documented choice (it is a policy control, not
  a security boundary, and there is no second layer behind it).
- **`age-derive.mjs` is `.mjs` + a hand-written `.d.ts`** because `node --test` cannot

- **`node --test` prints `ℹ pass` / `ℹ fail`, not `# pass`.** A grep for `^# (pass|fail)`

  happened here and was caught only by re-running.
